# v0.5.0 — Privacy Delivery Mode

Status: in progress. Written before the delivery-mode changes; the identifier taxonomy
(below, step 1) was implemented immediately before this document and is described here
as it stands.

## Goal

Yuhi stops being "a tool that hides everything" and becomes a runtime where the
**delivery policy is selectable**:

- external AI → protect direct personal identifiers
- business analysis → preserve the identifiers and attributes an analysis needs
- trusted local environment → deliver unchanged

Explicitly **out of scope**: Context Compression, Retrieval, the Evidence Ledger,
Dynamic Context and Native GUI. Privacy policy is added as a layer above them; none of
their code paths change.

The **document/PDF path is separate today**, which is the defect being fixed:

```text
background enqueue                        packages/core/src/prepare-workspace.ts
runBackgroundForRun()                     packages/core/src/background/wiring.ts
  buildSafetyPrimitives() → pseudonymizer = extractTabularIdentifiers(text) only
BackgroundPublisher.publish()             packages/core/src/background/publisher.ts
```

`extractTabularIdentifiers` calls `parseDelimitedTable` inside a `try`. Extracted PDF
prose is not a delimited table, so it throws, the `catch` returns `[]`, and the
pseudonymizer is handed an empty forbidden list — it replaces nothing and publishes the
raw extraction as a "Verified companion". Filed as issue #21.

## Minimal-change principle

1. **Do not replace the existing classifier.** `DirectIdentifierType` keeps deciding
   *what a column is*; the new taxonomy decides *what to do about it*. One function,
   `requiresPseudonymization(type)`, is the whole decision.
2. **Do not add a second policy engine.** The mode is a parameter threaded through the
   existing transform and the existing final gate.
3. **Do not fork the document path.** Reuse the same taxonomy, the same run registry
   and the same verification, with a prose de-identifier in place of the tabular one.

## Step 1 — Identifier taxonomy (implemented)

```text
DIRECT_PERSONAL_IDENTIFIER  → pseudonymize
  name, name-reading, email, phone, address,
  my-number, passport-number, government-id,
  bank-account, credit-card, biometric-id

OPERATIONAL_IDENTIFIER      → preserve
  student-id, student-card, employee-id, account-id, institutional-id,
  course-code, staff-id, application-number, record-id

ANALYTICAL_ATTRIBUTE        → preserve
  grade, score, evaluation, department, year, semester, attendance, …
```

`government-id` was split out of `institutional-id`: the old alias list mapped both
`governmentid` and `institutionalid` to one type, so a state-issued personal number was
treated the same as an internal record id. Under the taxonomy that would have preserved
a MyNumber and masked an order id — exactly backwards.

Financial and state numbers are matched **before** the generic `番号` morpheme rule,
which previously classified `口座番号` and `カード番号` as an operational `account-id`.

Verified against the requested fixtures:

```text
student_id,name,score / L001,山田太郎,90   →  L001, Student 001, 90
student_id,score      / L001,90            →  unchanged (no direct personal data)
course_code=990191, timestamp=11:13:14     →  unchanged
氏名,口座番号,マイナンバー                  →  Person 001, BANK-001, GOVID-001
```

## Step 2 — Delivery modes

```text
strict          mask direct personal identifiers; preserve operational + analytical
balanced        IDENTICAL transform to strict; differs only in surfaced wording
                (DEFAULT — per the CLI contract)
trusted-local   no pseudonymization, no identifier transformation
```

Note the spec states "strict = Default" in one place and `default: balanced` in the CLI
section. Resolved as: **default `balanced`**, and `strict` and `balanced` share one
transform implementation so they cannot drift. The difference is what each surface says.

`trusted-local` is **not** a security claim. Every surface must carry:

> Direct personal identifiers are delivered unchanged. Use only in trusted
> local/private environments.

## Step 3 — Run-scoped registry

`StudentAliasContext` already exists per run and is already shared across CSV/TSV/TXT
and XLSX (0.4.3 made it format-independent). What is missing is a way for a **prose**
de-identifier to reuse it, added as `directPersonalValueTokens(context)`: normalized
value → token, for direct-personal values only. Operational keys are absent because
nothing replaced them.

That is what makes one person carry one token in a CSV, a TXT, an XLSX and a PDF.

## Step 4 — Document/PDF pipeline

```text
extract  →  text representation  →  privacy transform  →  verification  →  delivery
```

Masking prose has a hard limit worth stating: structured identifiers (email, phone,
MyNumber, passport, bank, card) are pattern-detectable, and any name already seen in the
run's tabular data is maskable via the registry. A personal name that appears **only** in
prose, with no tabular counterpart, is not reliably detectable.

So the policy is: a companion is published **only when verification finds no residual
direct personal identifier**. Otherwise the document is kept local and reported as
context-unavailable. Publishing an unverified companion — today's behaviour — is what
issue #21 is about, and it is not made safe by relabelling it.

## Step 5 — Verification scope

The final gate currently reopens delivered CSV/TSV/TXT/XLSX. It must also cover:

- extracted document text
- companion markdown
- generated summaries
- handoff documents

Residual **direct personal** identifier → delivery blocked.
Residual **operational** identifier → allowed, by design.

## Acceptance

1. One policy across CSV/TXT/XLSX/PDF.
2. Names, addresses, phone numbers, email addresses removed before delivery in
   strict/balanced.
3. Student card, course code, employee number preserved.
4. Same person → same token across formats within a run.
5. No PDF companion carries raw personal information.
6. Final verification covers every delivered artifact.
7. Dynamic Context, Native GUI, Compression and Retrieval behave exactly as before.
