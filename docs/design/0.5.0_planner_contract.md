# v0.5.0 — Planner Contract

Companion to `0.5.0_dynamic_generation.md`. This document is the binding contract
for `packages/context-runtime/src/planner/`: the exact types, the rule evaluation
order, and what "conservative" means when the Planner is unsure.

## 1. Types

```ts
export type ContextIntent =
  | "debug" | "implement" | "test-failure" | "search"
  | "data-analysis" | "document-analysis" | "refactor" | "unknown";

export type ContextRole =
  | "load-bearing" | "supporting" | "reference"
  | "repeated" | "generated-noise" | "unknown";

export type ContextPlanKind =
  | "full" | "structured" | "window" | "reference" | "reuse" | "withhold";

export type ContextPlanReason =
  | "fits-budget" | "load-bearing" | "structured-representation"
  | "budget-pressure" | "already-delivered" | "retrievable-later"
  | "generated-noise" | "privacy-failure" | "verification-failure" | "unknown";
```

`ContextPlan.kind` drops `"summary"` from the directive's literal union (see
`0.5.0_dynamic_generation.md` §3) — deterministic summaries are a `structured`
plan executed by the existing JSON/test-output compressors, not a distinct
executor. Everything else matches the directive verbatim, including
`ContextPlan.confidence: "high" | "medium" | "low"`.

## 2. Classification is deterministic, signal-based, and allowed to be wrong

No LLM call, ever, in `classify.ts` — matching the competition review's rejected
list ("any non-deterministic model in the delivery path") and CLAUDE.md's
determinism requirements for anything in the delivery path. Signals available at
classification time, all already present in the gateway's request handling
(`packages/context-gateway/src/anthropic/request.ts`, `transform.ts`):

- the tool name (`read`/`grep`/`glob`/`bash`/`test`/`mcp`/`search`)
- the tool's own input (file path, extension, command string)
- the `ContentKind` already computed for compressor routing
- the most recent user message text (already in the request body Yuhi parses)
- prior deliveries in this session (Planner's own ledger, §4 below)

**Intent** is inferred from coarse, testable patterns only: a command matching a
test runner → `test-failure` candidate if the tool result also carries failure
markers (reuses the SAME test-output classification `test-output.ts` already
does, not a new failure detector); a file extension list associated with data
formats (csv/tsv/json/parquet-adjacent) → `data-analysis`; a PDF/DOCX/PPTX-derived
`pdf-companion` kind → `document-analysis`; `grep`/`glob` tool → `search`; a
recent user message containing an imperative verb set ("fix", "why does",
"error") → `debug`; a recent user message pattern matching "refactor"/"rename"/
"extract" → `refactor`; anything else → `unknown`. **A wrong intent must degrade
plan quality, never delivery safety** — every downstream rule that reads intent
only affects *which existing compressor/window/reference path runs*, never
whether privacy/secret scanning happens.

**Role** is inferred from a smaller, higher-confidence signal set: a file the
current turn is actively editing (from recent `tool_use` inputs naming that path)
→ `load-bearing`; a failing test's own output, a stack trace, the exact file
under test → `load-bearing`; a file share a strong name-based association with a
load-bearing file (adjacent test, adjacent config) → `supporting`; documentation,
design docs, large historical/generated artifacts → `reference`; a byte-identical
or substring-identical repeat of prior content this session → `repeated`
(computed from the Planner ledger, not guessed); build output, lockfiles, minified
bundles, and node_modules paths, and successful-test output with no failures →
`generated-noise`. **When classification confidence is not high, `role` is
`unknown`, never guessed toward `generated-noise`** — the directive's explicit
instruction ("分類に自信がない場合は、削除せず`unknown`として保守的に扱ってください")
is binding: `unknown` role NEVER routes to `withhold`, only Rule 1 (privacy/
security failure) can withhold.

## 3. Rule evaluation order (binding, matches directive §16 exactly)

```text
Rule 1  privacy/security failure                          → withhold
Rule 2  same object/revision/representation already delivered → reuse
Rule 3  small + load-bearing                               → full
Rule 4  verified structured compressor available            → structured
Rule 5  large + retrieval available + reference role        → reference
Rule 6  large prose/source                                  → window
Rule 7  fits maximum                                        → full
Rule 8  unknown + exceeds maximum                            → safe window/reference
Rule 9  fallback                                             → existing v0.4 behavior
```

Rules are evaluated top-to-bottom; the first matching rule wins. This is a literal
`if/else if` chain in `rules.ts`, not a scoring system — a scoring system would
make "why did the Planner pick this" require reasoning about weights instead of
reading a rule name, which breaks the explainability requirement (directive §17:
every delivery must record which rule fired). Rule 1 is evaluated from data the
Planner already receives (the runtime's own privacy/secret verdict, computed
BEFORE the Planner is invoked — see `0.5.0_dynamic_generation.md` §1's pipeline
order: classify/plan happens after privacy transform and scan, so "privacy
failure" here means the residue rescan / exact-output scan outcome the runtime
already computed, surfaced to the Planner as an input flag, not re-derived).

Rule 9 is not a `default:` case that silently does something new — it is
literally "call `compressWithFallback()` with the full `BUILTIN_COMPRESSORS`
registry," the exact call `deliver()` makes today. A test asserts Rule 9's output
is byte-identical to calling the pre-0.5.0 path directly on the same input.

## 4. Prior Delivery Ledger — contract

```ts
export interface PriorDelivery {
  readonly objectId: string;
  readonly revision: number;
  readonly representationId: string;
  readonly deliveredHash: string;
  readonly planKind: ContextPlanKind;
  readonly strategyId?: string;
  readonly estimatedTokens: number;
  readonly exactCharacters: number;
  readonly deliveredAtTurn: number;
}
```

Session-scoped, in-memory (mirrors `this.delivered`'s lifetime — not persisted
across a gateway restart in v0.5.0; the existing `this.delivered` map already
handles the "reproduce byte-identical output after restart" guarantee via
`restoreDelivered()`, and the Planner ledger is a superset used for Rule 2's
*plan*-level decision, not the byte-level prefix-stability guarantee, which stays
where it is). No raw content, ever — `deliveredHash` is a SHA-256, matching the
existing `EvidenceRecord.deliveredHash` field exactly (same hash function,
`sha256()` already defined in `pipeline.ts`).

## 5. Generation Cache — contract

```ts
export interface GenerationCacheKey {
  objectId: string;
  revision: number;
  privacyMode: PrivacyMode;
  secretDeliveryMode: SecretDeliveryMode;
  intent: ContextIntent;
  planKind: ContextPlanKind;
  strategyVersion: string;
}
```

Cache invalidation rules, tested explicitly (see `0.5.0_benchmark.md`'s test list
is NOT the right place — these are `planner/cache.test.ts` unit tests, listed here
for the contract record):

1. Same key → same bytes, always. If two calls with an identical key ever produce
   different bytes, that is a bug in the underlying compressor's determinism
   contract, not a cache bug — the cache test fails loudly rather than silently
   serving the second (different) result.
2. `revision` differs → cache miss, unconditionally.
3. `privacyMode` differs → cache miss, unconditionally, even if the resulting
   bytes would happen to be identical (e.g., content with no personal data at
   all under both Balanced and Trusted Local) — the KEY must differ, so the
   cache never becomes an implicit place where privacy mode stops mattering.
4. `secretDeliveryMode` differs → cache miss, same reasoning.
5. `strategyVersion` differs → cache miss (a compressor version bump invalidates
   its own cache entries; version is `${compressorId}@${compressorVersion}`,
   reusing the existing `strategy` string format from `pipeline.ts`).
6. `intent` differs → cache miss. Two different intents choosing the SAME
   `planKind`/`strategyVersion` for the SAME object could, in principle, produce
   identical bytes (the underlying compressor does not look at intent), but the
   key still differs — this trades a possible cache hit for a strictly simpler
   invariant ("the key is exactly what could have influenced the output"), and
   intent misclassification is exactly the kind of thing that should not silently
   share a cache slot with a correct classification.
7. A cache hit is a `reuse` plan (Rule 2), not a special ninth plan kind — the
   distinction between "prior-delivery-ledger reuse" and "generation-cache
   reuse" is an implementation detail of WHICH lookup found the hit; the plan the
   Planner emits is `{ kind: "reuse", reason: "already-delivered", reuseObjectId }`
   either way.

## 6. Repeated Work Observation — contract

`RepeatedWorkEvent` detection (directive §11) reads the SAME Planner ledger — no
second bookkeeping structure. "Exact repeated Read" = a `tool: "read"` event whose
`(objectId, revision)` matches a PriorDelivery from an EARLIER turn in this
session (not the live-zone cache hit, which already suppresses re-delivery cost;
this is about the AGENT choosing to re-read something it already has). "Contained
repeated Read" = a requested range that is a strict subset of a previously
delivered range for the same object. "Overlapping Read" = neither strict subset
nor disjoint. "Premature full suite" = a `test` tool event with no prior narrower
test-scoped command in this session's history for the same working tree state.

A `RepeatedWorkEvent` is recorded into the ledger and into session stats
unconditionally. Whether Claude sees a hint is a SEPARATE, much stricter gate:
only `count >= 2` for exact/contained repeats, and at most ONE hint per
`(objectId, type)` pair per session — the directive's "同じhintを繰り返さない"
is enforced by tracking which `(objectId, type)` pairs have already been hinted,
in the same ledger structure, not by a separate dedup cache.

## 7. What the Planner is never allowed to do

- Call a model (local or remote) to decide anything. Every rule input is a
  structural signal already computed elsewhere in the pipeline.
- Mutate or re-encode content. `ContextPlan` names a strategy; execution stays in
  `@yuhi/context-compression`/`@yuhi/context-store`.
- Drop load-bearing content because of budget pressure (§4 of the sibling doc).
- Emit raw content into evidence. `ContextPlan.reason` and `strategyId` are safe
  strings; nothing in the plan structure carries a content value.
- Change behavior in `"observe"` mode. The plan is computed and recorded; the
  executed path is byte-identical to `generationMode: "off"`.
