# v0.5.0 — Benchmark Plan and Release Gate

Companion to `0.5.0_dynamic_generation.md`. Extends `@yuhi/context-benchmark`
(existing three-condition harness, `packages/context-benchmark/scripts/`) rather
than building a second framework, per directive §21.

## 1. What v0.4.0's own measured data already tells us

`V0_4_0_DYNAMIC_RUNTIME.md` recorded real, provider-measured results this design
must not contradict or re-litigate without new evidence:

- Registering MCP retrieval tools costs a fixed ~507 tokens in every cached
  system prompt, PLUS a larger *behavioral* cost (extra turns) that varied by
  task and by model. This is why retrieval defaults to `disabled` today and why
  v0.5.0's `reference` plan kind must be measured with retrieval OFF as the
  baseline comparison, not assumed to be free because "it's just a pointer."
- Grep/search compression fired in only 1 of 3 real sessions (Claude Code's own
  tool defaults return file names, not content, most of the time) — a `search`-
  intent classification in the Planner must not assume search results are
  usually large; Rule 4 (structured) only fires when a compressor's `verify()`
  actually accepts the input, exactly as today.
- A `Read` of a log/prose file is the agent SCANNING, and restructuring it costs
  MORE turns, not fewer (measured: turns 7→9-16, cost +75% before the scan guard;
  +23% after). The Planner's `window`/`reference` plans for `Read` of log/text/
  markdown must inherit the SAME scan-guard ceiling
  (`DEFAULT_SCAN_GUARD_MAX_TOKENS`, `transform.ts`) — this is not re-derived,
  it is reused verbatim as an input to Rule 6/Rule 8.
- Token reduction and cost reduction diverge by model (haiku: −20% cost on a
  −15% token cut; sonnet: parity on the same token cut) because cache-read vs.
  output pricing differs. Every v0.5.0 benchmark table must report both model
  classes separately, exactly as v0.4.0's tables do, and must never present a
  haiku result as if it generalizes to sonnet.

## 2. Conditions (directive §21, unchanged)

```text
A. Baseline Claude Code
B. Yuhi Static
C. Yuhi Dynamic v0.4
D. Yuhi v0.5 Observe   (plan computed, v0.4 path executed — isolates plan quality
                          from execution risk: if D's task success/cost differs
                          from C at all, that is a harness bug, since Observe must
                          be byte-identical to v0.4 by construction)
E. Yuhi v0.5 Active
```

Condition D is a correctness check on the harness as much as a benchmark
condition: `0.5.0_dynamic_generation.md` §2 states Observe mode never changes the
executed path, so D vs. C must show zero delta on every metric except the new
evidence fields. A nonzero delta on task success, tokens, or cost between C and D
means the "observe never executes the plan" invariant broke, and is treated as a
Stop Condition (directive §30), not a benchmark result to publish.

## 4. Runs

Per directive: Haiku-class n=3 per condition per fixture; Sonnet-class high-value
fixtures only (3, 4, 8, 9 — the ones with a pre-existing v0.4.0 measured baseline
or a budget-pressure question that is plausibly model-sensitive) at n=3. Cost-
constrained smoke first: 4 fixtures (2, 3, 4, 9 — one of each rule family) × n=1,
grader-checked, before the full matrix.

## 5. Metrics — unchanged list from directive §21, plus two v0.5-specific columns

`generation plan counts` (per kind: full/structured/window/reference/reuse/
withhold) and `prefix stability violations` were already directive-listed;
v0.5.0 additionally reports **plan-vs-execution agreement** (Observe mode only:
does D's computed plan match what C would have done, expressed as a percentage —
this is the plan-quality signal that exists independent of whether Active ships)
and **cache hit rate** (Generation Cache hits / total plan-2-eligible deliveries).

## 6. This session's execution constraint — stated plainly, not glossed over

`@yuhi/context-benchmark`'s real-Claude scripts (`real-claude-run.mts`,
`matrix.mts`) invoke the actual `claude` CLI against `api.anthropic.com` with a
real API key and real billing, exactly as `V0_4_0_DYNAMIC_RUNTIME.md`'s numbers
were produced. **This development environment has no `claude` CLI installed and
no Anthropic API credentials** (confirmed during v0.4.8's own release smoke test:
`yuhi launch claude --dynamic-context` correctly starts the gateway and resolves
privacy mode, then fails at "Claude Code is not installed" — the same constraint
applies here). Phase 7 of this directive therefore:

- Extends the benchmark harness and adds the 10 fixtures listed above as real,
  runnable scripts and prompts (so a maintainer with credentials can run them
  unmodified).
- Runs everything that does NOT require a live model call: fixture setup
  correctness, harness plumbing, the Observe-mode plan-computation itself
  (deterministic, no model needed — the Planner's rules can be exercised and
  asserted against synthetic `PlannerInput` values in ordinary unit tests, which
  IS done, extensively, in Phase 1–5).
- Does **not** fabricate, estimate, or extrapolate a token/cost/success table for
  conditions A/B/C/D/E. No number appears in this document, the CHANGELOG, or any
  README claiming a measured reduction or cost delta for v0.5.0, because none was
  measured. This is the honest reading the directive's own §27 (Prohibited
  Claims) requires, and it is why the release-gate decision below is `observe`,
  not `active` — the gate in §22 requires PASS on provider-measured metrics that
  this environment cannot produce.

## 7. Release gate decision for this Release Candidate

Per directive §22's own instruction — "条件を満たさない場合: generation-mode
default = observe" — and given §6 above, this Release Candidate ships with:

```text
generation-mode default = observe
active = opt-in, undocumented as a headline feature until benchmarked
```

This is not a failure of the gate; it is the gate working as designed. The
maintainer (or a future session with real API access) runs the fixtures in §3
against the harness extended in this phase, fills in the table this document
deliberately leaves blank, and only then flips the default — exactly the
sequencing `0.5.0_dynamic_generation.md` §8 commits to in the design.
