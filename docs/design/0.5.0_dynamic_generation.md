# v0.5.0 — Task-Aware Dynamic Context Generation

Prerequisites: `V0_4_0_ARCHITECTURE.md`, `V0_4_0_DYNAMIC_RUNTIME.md`,
`V0_4_0_COMPETITION_REVIEW.md`, `../adr/0005-dynamic-content-type-priority.md`,
`0.4.8_privacy_mode.md`, `0.4.8_measurement_reliability.md`.

## 1. What changes, and what does not

v0.4.8's `ContextRuntime.deliver()` already runs a full pipeline per tool result:
privacy transform → secret/PII/metadata scan → **one fixed compressor chosen by
content-type routing** → exact-output rescan → evidence → delivery
(`packages/context-runtime/src/pipeline.ts`). The compressor registry
(`packages/context-compression/src/registry.ts`) picks the first compressor whose
`supports()` matches and whose `verify()` passes — a static, content-type-only
decision that has no idea what the agent is doing, whether this exact content was
already delivered, or how much budget is left.

v0.5.0 inserts a **Planner** between "safety-cleared content" and "which
compressor/strategy runs": the same compressors, the same store, the same
retrieval, the same evidence ledger — a new *decision* stage, not a new pipeline.

```text
tool result
  → private store (unchanged)
  → privacy transform (unchanged)
  → secret/PII/metadata scan (unchanged)
  → classify: content type / intent / role                    [NEW]
  → Planner: ContextPlan (kind, reason, strategy)              [NEW]
  → execute plan via EXISTING compressor/store/retrieval       [reuses registry.ts]
  → exact-output rescan (unchanged)
  → evidence (unchanged, extended with plan fields)
  → delivery (unchanged)
```

Nothing upstream of "classify" or downstream of "execute plan" changes. Safe Apply,
the privacy taxonomy, secret scanning, the Native GUI broker, and Claude Code
authentication are untouched by construction, because the Planner sits entirely
inside the segment of `deliver()` that today calls `compressWithFallback()`
directly — it becomes one more caller of the same registry.

## 2. Where the Planner lives

Per directive §15, a new package is created only if the existing runtime cannot
host the Planner cleanly. It can: `ContextRuntime` already owns the compressor
registry call site, the prefix-stability map (`this.delivered`, doubling as a
starting point for the prior-delivery ledger), and the measurement context
(`this.ctx.estimateTokens`). The Planner ships as
`packages/context-runtime/src/planner/` — a module, not a package — with:

```text
planner/types.ts       ContextIntent, ContextRole, ContextPlan, PlannerInput
planner/classify.ts     intent + role classification (deterministic, no LLM)
planner/rules.ts        the Planner Rules v1 decision function
planner/ledger.ts        PriorDelivery tracking (in-memory, session-scoped)
planner/cache.ts         GenerationCacheKey + byte-identical reuse
planner/repeated-work.ts  RepeatedWorkEvent detection
```

`ContextRuntime.deliver()` gains one branch point: when a `generationMode` other
than `"off"` is configured, it builds a `PlannerInput`, calls `plan()`, and in
`"observe"` mode records the counterfactual plan in evidence without changing the
executed path; in `"active"` mode the plan's `kind`/`strategyId` selects which
existing compressor/window/reference/reuse path actually runs. `"off"` (the
pre-0.5.0 default codepath) never constructs a `PlannerInput` at all — a
zero-overhead escape hatch, not a flag check inside the hot path.

## 3. Planner boundary — what it does and does not do

The Planner **never rewrites content**. Its output (`ContextPlan`) is a decision
record: which existing strategy to run, and why. Content transformation stays
entirely inside `@yuhi/context-compression`'s compressors, `@yuhi/context-store`'s
range/JSONPath resolution, and the existing retrieval path
(`ContextRuntime.retrieveByObject`). This mirrors the same separation the
competition review already committed to for ranking (`context-ranking` computes
weights, never mutates a file) and keeps the Planner audit-cheap: reviewing "did
the Planner pick the right existing tool" is a much smaller surface than
reviewing "did the Planner correctly reimplement compression."

Concretely, `ContextPlanKind` maps onto pre-existing machinery:

| Plan kind | Executed by |
|---|---|
| `full` | `compress: false` path (already exists — `req.compress === false`) or the scanned original when compression yields `no-reduction` |
| `structured` | `compressWithFallback()` restricted to the structured compressors (`jsonCompressor`, `testOutputCompressor`, `searchResultsCompressor`) |
| `window` | `safeWindow()` (already exists) or the `textCompressor`'s byte/line window |
| `reference` | an omission is recorded and NOT inlined; the agent retrieves it via the existing `retrieveByObject` path |
| `reuse` | `this.delivered` (already exists, prefix-stability map) returns the pinned bytes without re-running any compressor |
| `withhold` | the existing `withhold()` path |

No new content representation is invented. `summary` (directive §7) is
deliberately **not** implemented as its own executor in v0.5.0 — the directive
explicitly restricts it to "existing deterministic summary" only (schema, counts,
failure-only summary), which is exactly what `jsonCompressor` and
`testOutputCompressor` already produce. `summary` therefore is not a distinct
`ContextPlanKind` value at all; those cases resolve to `structured`. This is a
deliberate simplification from the directive's literal type union, recorded here
rather than left implicit (mirroring the JSON-masking precision decision in
`0.4.8_privacy_mode.md`).

## 4. Budget semantics

`RuntimeBudgetState` (directive §8) is additive and optional. When
`context.runtimeBudget` is unset in `yuhi.yaml` and no `--context-budget`/
`--context-max` CLI flag is given, the Planner never sees a budget object at all —
`PlannerInput.budget` is `undefined`, and Rule 7/Rule 9's fallback path is
identical to v0.4.8 behavior (`compressWithFallback()` with `tokenBudget` only from
`req.tokenBudget ?? this.tokenBudget`, exactly as today).

When a budget IS configured, the measurement method is fixed for the session at
gateway startup (`currentMeasurementMethod()`, v0.4.8 Phase 5) and never changes
mid-session — switching estimators mid-session would make "delivered so far"
non-comparable to "target," corrupting every subsequent budget decision. Exact
character/byte counts (`byteCount`/`codePointCount`) are always recorded alongside
the estimate, so a post-hoc audit never depends on the heuristic being right.

Budget pressure changes ONLY the priority order the Planner searches
(load-bearing kept, repeated content reused, reference-role content pointed at
instead of inlined, supporting content structured/windowed, unknown content kept
full/windowed rather than dropped) — it is never a reason to silently drop
load-bearing content. This mirrors `CLAUDE.md`'s governing invariant for Static
Prepare ("file blocked ≠ launch blocked") applied to the dynamic path: "budget
pressure ≠ silently missing evidence."

## 5. Cache key and prefix stability

The Generation Cache (directive §9) sits ALONGSIDE the existing prefix-stability
map (`this.delivered: Map<"objectId#revision", DeliveredBytes>`), not as a
replacement. The existing map answers "is this exact (object, revision) already
pinned for THIS session, regardless of plan" — the invariant that makes live-zone
re-emission cheap. The Generation Cache answers a narrower question: "would this
(object, revision, mode, intent, plan-kind, strategy) combination, if planned
again, produce byte-identical output" — used by the Planner's Rule 2 (reuse) to
decide, before running a compressor, whether the prior delivery already satisfies
this request.

Privacy mode changing is **never** a cache hit under either mechanism — this
already holds for `this.delivered` today only incidentally (a fresh
`ContextRuntime` per privacy mode), and the Generation Cache makes it an explicit,
tested invariant (`privacyMode`/`secretDeliveryMode` are part of the key) so a
future refactor cannot silently reuse Balanced-masked bytes under Trusted Local.

## 6. Retrieval integration

REFERENCE and WINDOW plans that omit content use the SAME retrieval path that
already exists (`ContextRuntime.retrieveByObject`), which already re-applies the
current privacy policy and secret policy on every fetch (v0.4.8, `pipeline.ts`
§5b). No new retrieval server, no new locator grammar. The Planner's only
retrieval-relevant decision is whether to CHOOSE the reference/window kind in the
first place; once chosen, retrieval behaves exactly as it does in v0.4.8, and the
existing round-trip test (`PERSON-001` survives retrieve, never reverts to raw)
covers the v0.5.0 path with no new test needed for the privacy half — only new
tests confirming the Planner's REFERENCE decision correctly produces a
retrievable locator, which is a Planner-output test, not a retrieval test.

## 7. Failure fallback

Rule 9 (fallback → existing v0.4 behavior) is not a last resort bolted onto the
Planner; it is what "generation-mode off" already IS. `"observe"` mode computes a
plan for evidence only and always executes the v0.4 path, so a Planner bug in
observe mode cannot change a single delivered byte — this is the mechanism, not a
promise. `"active"` mode is the only mode where a Planner defect could reach
delivery, and every Planner rule that is not explicitly one of Rules 1–8 falls
through to Rule 9, which is byte-for-byte the v0.4.8 `deliver()` compression call.
A Planner that cannot classify (`intent: "unknown"`, `role: "unknown"`) still
produces a valid plan — Rule 8's "safe window/reference" — never an exception that
would leave `deliver()` without a delivery.

## 8. Benchmark gate, restated from the directive

Per directive §22, `"active"` becomes the CLI/VS Code default only when the
release-gate table passes against real, provider-measured runs. This document
does not restate the gate table (see `0.5.0_benchmark.md`); it records the
consequence for design: every `ContextPlanKind` must be safe to ship with
`generation-mode=observe` as the shipped default, because that is very likely to
be the v0.5.0 GA state — the design must not assume Active ships.
