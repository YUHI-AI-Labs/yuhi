# 0.4.8 — Privacy Mode product surface

Status: in progress (Phase 1 of 6). This document records the decisions made during
implementation, in the order they were made, so a later change does not silently
reinterpret them.

## The one rule

> v0.4.8 does not build a new privacy engine. It makes the Privacy Taxonomy (0.4.6)
> and the Document Privacy Pipeline (0.4.7) selectable, visible, and consistent across
> every surface that delivers context to an agent: Static Prepare, Dynamic Terminal,
> and Native GUI Mode.

Three modes, one name everywhere: **Balanced** (default) / **Strict** / **Trusted
Local**.

## Decision 1 — Privacy Mode and Secret Delivery are two separate policy axes

This is the load-bearing decision of Phase 1, discovered rather than assumed.

**What was found**, before any code was written: Static Prepare (`prepareWorkspace()`)
redacts every detected secret today, **unconditionally, in every existing Safety
Mode** — `packages/config/src/defaults.ts`'s `redact-detected-secrets` default policy
rule fires on detector match alone; `applySafetyMode()` never touches it. There is no
"secrets may reach the agent" concept in Static Prepare at all, and never has been.
"Developer Mode" — the contract that a `.env` value may reach the agent because the
developer needs it for the work — has only ever existed for Dynamic Context sessions
(`packages/context-runtime/src/delivery-policy.ts`).

**What that means for the naive reading of the original directive:** applying
"Balanced preserves the Developer Mode contract" literally to Static Prepare would
have made `yuhi prepare` (Balanced, the default, the most common invocation) stop
redacting `.env` secrets by default — a real regression to the safety of the single
most-used code path, not a wording change.

**Decision (confirmed with the maintainer before writing any Phase-1 code):** Privacy
Mode and secret delivery are resolved as two independent inputs, composed per
`PrivacySurface`:

```text
Surface            Balanced             Strict    Trusted Local
static-prepare      redact               redact    redact   <- ALWAYS redact
dynamic-terminal     developer-delivery   redact    developer-delivery (ack'd)
native-gui           developer-delivery   redact    developer-delivery (ack'd)
```

Static Prepare's existing, unconditional secret redaction is **never weakened by this
feature**, in any mode, including Trusted Local. Trusted Local disables PERSONAL
IDENTIFIER transformation only, on every surface — it does not disable secret
redaction on `static-prepare`. This is why Trusted Local's user-facing copy must be
surface-specific: on Static Prepare, "secrets are still redacted from the prepared
workspace"; on a dynamic surface, "personal identifiers and development secrets may be
delivered unchanged". A single shared string would lie on one surface or the other —
see `PRIVACY_MODE_COPY`'s replacement, `privacyModeCopyFor(mode, surface)`, in
`packages/shared/src/privacy-mode.ts`.

## Decision 2 — two-step resolution, not one function

`packages/shared/src/privacy-mode.ts` splits resolution into:

1. `resolvePrivacyPolicy({ candidates, trustedLocalAcknowledged })` — **which** mode
   wins (Section 5 precedence: CLI > VS Code selection > workspace config > legacy
   mapping > default) and the Trusted Local acknowledgement gate. Throws
   (`PrivacyModeResolutionError`) on an invalid mode string or an unacknowledged
   Trusted Local selection — never a silent fallback to a different mode.
2. `resolveDeliveryPolicy({ privacyMode, surface, warningAcknowledged, source })` —
   given an ALREADY-VALID mode + a `PrivacySurface`, compose the full
   `ResolvedDeliveryPolicy` (identifier transform + `secretDeliveryMode`). Pure and
   non-throwing: by the time this runs, step 1 already decided the selection is
   allowed, so this function never rejects a call, even
   `{ privacyMode: "trusted-local", surface: "static-prepare" }` with no
   acknowledgement passed — it just returns `secretDeliveryMode: "redact"` (Static
   Prepare's real, unconditional behavior) and `warningAcknowledged: false`, honestly
   reflecting the input rather than asserting a gate this function does not own.

`PrivacyMode` itself, its guard, and the per-identifier transform decision
(`modeTransformsDirectIdentifiers`) were not created new — they already existed in
`packages/shared/src/identifier-taxonomy.ts`, scaffolded ahead of schedule with a
comment noting "strict and balanced apply an identical transform, they differ only in
what each surface says". Phase 1 reuses that type rather than redefining it.

## Legacy mapping

`DeliveryMode` ("developer" | "strict", Dynamic Context only) maps via
`privacyModeFromLegacyDeliveryMode`:

```text
deliveryMode=developer  -> privacyMode=balanced  -> (on a dynamic surface) secretDeliveryMode=developer-delivery
deliveryMode=strict     -> privacyMode=strict     -> secretDeliveryMode=redact
```

`developer` never maps to `trusted-local`: Developer Mode's contract was "secrets may
reach Claude for development work", not "personal identifiers are unmasked". Widening
it on migration would silently remove identifier protection a Developer Mode user
never asked to give up. Static Prepare has no legacy `deliveryMode` to map from — it
never had a Developer Mode concept.

## Known limitations (carried from 0.4.7, unchanged by this feature)

Name detection remains CJK 2–4 character shape only (no Latin-script names, no
single/5+ character CJK names) — see `docs/design/0.4.7_document_privacy.md`. Privacy
Mode selects WHETHER identifiers are transformed; it does not change WHAT the
underlying detector can recognize.

**JSON key-based masking requires a record shape (v0.4.8, added during release
verification).** A JSON object with a direct-personal field (`name`, `address`, …) and
NO recognized operational sibling key in the SAME object (`student_id`, `course_code`,
…) is masked only on shape-detectable fields (email/phone/my-number/etc.) — the
personal field itself is left unmasked. `{"name": "...", "email": "...", "message":
"..."}` masks `email` only. See "JSON precision decision" below for the full rule and
rationale. **"All JSON personal identifiers are transformed" is not an accurate claim
and must not be made in release copy.**

## Decision 3 (Phase 3): Dynamic Context needed a REAL transform, not a displayed policy

Phase 3 research found that `ContextRuntime.deliver()` (`packages/context-runtime`)
already had full, tested secret-delivery policy machinery (`DeliveryPolicy`,
`redactSecretsBeforeDelivery`) but **no direct-personal-identifier transformation of
any kind** — Dynamic Context has never masked a name, email or phone number in a live
tool result. Wiring only `ResolvedDeliveryPolicy.transformDirectPersonalIdentifiers`
into a banner/manifest field, without an underlying transform, would have made
Balanced/Strict CLAIM protection that did not exist — exactly the "no display-only
policy" failure this feature must not ship. Confirmed with the maintainer before
writing code; the directive was to build the real transform, reusing 0.4.6/0.4.7's
taxonomy rather than a new engine (`packages/shared/src/text-deidentify.ts`,
`student-records.ts`), scoped as **Phase 3A** (runtime transform, this section) then
**Phase 3B** (CLI/session-level propagation).

### JSON precision decision (revised during release verification — see below)

The obvious approach — reuse `classifyStudentRecordHeaders` to mask any JSON field
whose KEY looks like `name`/`email`/etc. — was tried against the existing
`pipeline.test.ts` regression suite and rejected: a live Dynamic Context session
proxies arbitrary tool output from arbitrary repositories, where a JSON `"name"` field
is far more likely to be a package/product/test-fixture name than a person's. Key-name
masking broke the existing `retrieval.text).toContain("user-500")` regression
assertion and would over-mask ordinary API/code JSON in real use. Confirmed with the
maintainer; the FIRST shipped design (`deidentifyJsonFields`,
`packages/shared/src/text-deidentify.ts`) was **shape-based only**: every JSON string
value got the same PATTERNS (email/phone/my-number/passport/credit-card) and
registry-reuse treatment prose gets, regardless of the key it lives under. A bare
`"name": "user-500"` was left unchanged (no shape match, no registry link); an email
value was masked under any key.

**Revised during the v0.4.8 release verification pass**: this was too conservative. A
live empirical audit found `deidentifyJsonFields` never masked a `name` key even for
`{"student_id":"L001","name":"山田太郎","score":90}` — an unambiguous student-record
shape, isomorphic to a CSV row Static Prepare already masks. The shipped rule now adds
one narrow, evidence-based case: a direct-personal key (`name`, `address`, …) is
masked by key ONLY when the SAME JSON object's own keys also contain a recognized
OPERATIONAL identifier (`student_id`, `course_code`, `employee_id`, …) — the identical
classification (`classifyStudentRecordHeaders` + `identifierCategory`) that already
makes a CSV row "restricted" (sensitive). A bare `"id"` does not count as the
operational signal (excluded deliberately — it matches only a generic
trailing-morpheme fallback that fires on almost any object, which reintroduced the
exact over-masking risk this whole design avoids). See `GENERIC_OPERATIONAL_TYPES` in
`packages/shared/src/text-deidentify.ts`.

**Known limitation, stated plainly**: a JSON object carrying direct personal data with
NO recognized operational sibling key — e.g. `{"name": "...", "email": "...",
"message": "..."}` — is masked ONLY on the shape-detectable fields (`email` here); the
`name` value is NOT masked, by design, because nothing in that object's shape
distinguishes it from an arbitrary product/API/test-fixture record. This is the same
precision trade-off the whole JSON design makes, stated as a boundary rather than left
implicit: **"All JSON personal identifiers are transformed" is not a permitted claim.**
The accurate claim is "JSON fields are masked by shape (email/phone/etc.) always, and
by key when the object is record-shaped (an operational key present alongside a
personal one)."

### Content routing

`packages/context-runtime/src/privacy-pipeline.ts`'s `classifyDeliveryContent` routes
a live tool result by the store's own `ContentKind` (csv/tsv → tabular taxonomy;
json → `deidentifyJsonFields`; markdown/pdf-companion → full prose de-identification
including the CJK name heuristic; log/test-output/shell-output/git-diff/html/xml/source
→ shape-patterns only, CJK name heuristic OFF, to avoid over-masking source code and
command output; `text`/`source` disambiguated by shape into configuration/table/prose).
`deidentifyText` gained a `{ includeNameHeuristic?: boolean }` option (default `true`,
unchanged for every existing caller) so source/command-output surfaces can reuse the
same function without the heuristic.

### Pipeline order (implemented exactly as specified)

`ContextRuntime.deliver()`: raw → private store (`store.put`, unchanged — the RAW
bytes are the only thing that may exist there) → content classification → direct-
personal transform → secret scan/redaction → compression → **direct-personal residue
rescan** (new; Balanced/Strict withhold on residue, Trusted Local exempt by design,
mirroring the existing exact-output secret rescan) → evidence → delivery.
`retrieveByObject()` re-applies the SAME transform to every resolved range using the
runtime's CURRENT `privacyMode`/`aliasContext` — never returns raw bytes for a range
that was masked at delivery time — then re-runs the residue check before caching.

### Evidence

`EvidenceRecord` gained `privacyMode`, `secretDeliveryMode`, `directIdentifiersDetected`,
`directIdentifiersTransformed`, `directIdentifierResidue`, `privacyTransformationApplied`,
`privacyVerificationPassed`, `privacyFallback` — all optional/additive, never a raw
value. `Delivery` (status `"delivered"`) gained `privacyMode`/
`directIdentifiersTransformed` alongside the existing `secretRedactions`, kept as a
SEPARATE field from secret/compression stats per the no-mixed-stats requirement.
