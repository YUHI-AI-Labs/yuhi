# v0.4.8 — Measurement Reliability

## Context

Originally scoped as a separate v0.4.9 release, merged into v0.4.8 by the maintainer's
own scope-extension directive ("v0.4.8 Scope Extension: Privacy Mode + Measurement
Reliability"). Implemented as Phase 5, after Privacy Mode Phases 1–4 were complete and
committed.

The directive's ask was broad: a `MeasurementMethod` taxonomy, exact byte/Unicode
code-point counting, extending the existing `setTokenEstimator` seam, content-type
calibration profiles for seven content categories (dense-json, structured-text,
japanese-prose, english-prose, source-code, command-output, generic-fallback),
reduction-calculation rules that never compare different units/methods,
privacy-transformation-delta vs structural-compression-delta separation, a manifest
measurement schema, CLI/VS Code copy updates, and an audit of existing token/cost
claims across README ×3, the Marketplace listing, the site, the CLI and VS Code.

Research before writing any code (`packages/shared/src/tokens.ts`,
`packages/context-compression/src/contract.ts`, `packages/core/src/savings.ts`,
`packages/core/src/public-prepared-summary.ts`, and a grep of every numeric claim in
`README.md`, `apps/*/README.md`, `site/*.html`) found the actual state of the codebase
was more specific and more actionable than the broad ask: there were real, concrete,
fixable measurement BUGS already in the code, and the existing UI copy was already
disciplined about labeling estimates as estimates. That changed the shape of this
phase from "build seven calibration profiles from scratch" to "fix the measurement
bugs the broad ask was actually protecting against, and scope the rest honestly."

## Decision: scope to verifiable, well-justified fixes; flag the rest

Two of the seven content-type calibration profiles the directive asked for
(`japanese-prose`, and implicitly the CJK handling inside every other profile) rest on
a single, well-established, defensible fact: mainstream BPE tokenizers (Claude's
included) split CJK text far denser than the codebase's flat `chars/4` heuristic
assumed — closer to 1–2 characters per token, not 4. Building the other five profiles
(dense-json/structured-text/source-code/command-output/generic-fallback) would require
empirical calibration data — running real content through a real tokenizer and fitting
divisors — that this session had no way to obtain. Shipping five more divisor
constants with no calibration data behind them would have been exactly the
"unsubstantiated claim" this phase exists to remove, dressed up as a feature. The
decision made here: implement the ONE calibration axis that is defensible without new
data (CJK vs. non-CJK), and flag the rest as deferred rather than fabricate precision.

Similarly, the README/site/Marketplace claims audit (Section B below) surfaced real,
concrete findings — but rewriting a `-13% provider cost` or `94% reduction` headline
number requires either re-running the benchmark that produced it or trusting a number
this session cannot verify. Silently leaving a possibly-stale number and silently
rewriting an unverifiable one are both wrong for different reasons. The decision:
report the findings precisely (file:line, what's duplicated where, what's unverifiable)
rather than either.

## What shipped

### A. `MeasurementMethod` taxonomy + exact vs. estimated split (`packages/shared/src/tokens.ts`)

```ts
type MeasurementMethod = "chars-per-token-heuristic" | "cjk-weighted-heuristic" | "exact-tokenizer";
```

`TokenEstimate` now reports `bytes` (exact, `Buffer.byteLength(text, "utf8")`) and
`codePoints` (exact, iterates code points — `string.length` over-counts anything
outside the BMP) alongside the existing `chars` (UTF-16 code units, kept for backward
compatibility) and the estimated `tokens`, each tagged with `method` and `approx`. The
module's own doc comment states the rule plainly: byte/code-point counts can be exact;
token counts cannot, until a real tokenizer is injected — and the two must never be
presented as the same kind of number.

### B. CJK-weighted default estimator, replacing the flat `chars/4` default

`estimateTokensCjkWeighted` counts CJK code points (Unified Ideographs, Hiragana,
Katakana, Hangul) and non-CJK code points separately, weighting CJK at ~1.5 chars/token
and everything else at ~4 chars/token — deliberately conservative, not 1:1, because
this is still a heuristic. Numerically IDENTICAL to the old `estimateTokens` for
pure-ASCII/Latin text — nothing changes for the common non-CJK case. This is now
`activeTokenEstimator`'s default; `estimateTokens` (the old flat heuristic) is kept as
an explicitly-named, still-usable option for comparison or opt-out.

This directly targets the product's own stated primary use case (Japanese student
records — see `README.ja.md`, the CJK name-detection heuristic in
`packages/shared/src/text-deidentify.ts`): the flat heuristic systematically
UNDER-counted tokens for CJK content, which meant "reduction %" numbers looked BETTER
than they actually were on the exact content this product exists to handle.

### C. Fixed the split `setTokenEstimator` seam

Research found `setTokenEstimator()` had **zero non-test call sites** anywhere in the
repo, and — more importantly — even if called, it silently did nothing for Dynamic
Context: `packages/context-compression/src/contract.ts`'s `defaultCompressContext()`
imported the raw `estimateTokens` function directly at module load, not
`activeTokenEstimator`, so `ContextRuntime.deliver()`'s `tokensBefore`/`tokensAfter`
and the gateway's `dynamicReduction` metric were PINNED to the old heuristic
regardless of what a caller configured. Static Prepare (via `tokenEstimate()`) always
read `activeTokenEstimator` live. Fixed by making `defaultCompressContext`'s default
delegate to `activeTokenEstimator` on every call (`(text) =>
activeTokenEstimator(text)`), not a snapshot — matching `tokenEstimate()`'s own
behavior exactly, so both surfaces stay in sync with whatever estimator is configured,
including the new CJK-weighted default.

### D. Fixed `savings.ts`'s clamping-to-zero bug

`packages/core/src/savings.ts`'s `contextSavings()` (the `yuhi status` pre-prepare
estimate) computed `tokenReductionPct` with `Math.max(0, ...)`, silently flooring any
case where the visible set is larger than the source. This directly contradicts the
codebase's own documented rule (`docs/HANDOFF.md`: *"Reduction is not clamped.
Negative reduction is real... CLAUDE.md permits 0.0% only when before is zero"*) and
the sibling `reductionReport()`'s own doc comment making the same promise. It was the
one formula in the codebase that violated its own stated policy. Fixed by removing the
clamp; the CLI's existing `if (savings.tokenReductionPct > 0)` display guard
(`apps/cli/src/render.ts`) already omits the bullet rather than showing a wrong number
for a non-positive value, so no display code needed to change — the DATA is honest now,
where before it was silently wrong.

### E. Manifest measurement schema (`PublicPreparedContextSummary`)

Added `tokenEstimationMethod: MeasurementMethod | null` and `tokenEstimationApprox:
boolean | null` to the existing `publicSummary` block in `manifest.json` (extended, not
duplicated — the manifest already had TWO overlapping token/reduction blocks per the
research; this phase did not add a third). A manifest reader can now tell WHICH
estimator produced `originalEstimatedTokens`/`reductionPercent`, not just the numbers
themselves — the "manifest measurement schema" ask from the directive, done as an
additive extension of the single existing consumer (CLI, VS Code, and handoff docs all
already read this one block per `docs/HANDOFF.md`'s single-source-of-truth pattern).

### F. Privacy-transformation-delta vs structural-compression-delta separation

Already substantially addressed by Phase 3A (this same v0.4.8 effort): Dynamic
Context's `EvidenceRecord` carries `directIdentifiersTransformed`/
`directIdentifierResidue` as fields SEPARATE from `secretRedactions` and the
compression `tokensBefore`/`tokensAfter`, exactly the separation this directive asks
for, applied to the live-delivery surface. Static Prepare's per-file manifest entries
already separate these dimensions via `transformations` (an array naming which
transforms ran — `"summarized"`, `"pseudonymized"`, `"masked"`) and `maskedValues`
(a count) as fields distinct from the aggregate `beforeChars`/`afterChars`, which is
itself only ever a structural before/after, not a privacy-transformation count. No
further schema change was needed here; this section records that the ask was already
met, rather than silently skipping it.

## What was NOT built, and why

- **The other five content-type calibration profiles** (dense-json, structured-text,
  english-prose, source-code, command-output) — no calibration data available this
  session; see the Decision section above. `packages/context-runtime/src/
  privacy-pipeline.ts`'s `classifyDeliveryContent` (built in Phase 3A) and
  `packages/context-compression/src/registry.ts`'s compressor dispatch already
  classify content by shape for OTHER purposes and could seed this work later, but
  building a fourth, unvalidated classification vocabulary specifically for token
  calibration was judged worse than not building it.
- **CLI/VS Code copy rewrites** — the research found the existing copy already
  disciplined (`apps/vscode/src/activity-panel.ts`'s own doc comment: *"never round a
  genuine, tiny reduction... labelled EXACTLY 'Estimated context reduction' — never
  billing/API/cost savings"*). No specific inaccuracy was found that a rewrite would
  fix; the underlying NUMBERS were the actual problem (Sections B–D), not the wording
  around them.
- **The README ×3 / Marketplace / site claims audit** — see below. Reported, not
  edited.

## Claims audit findings (reported, not acted on)

Concrete numeric claims found duplicated with no single source of truth, each
appearing in 2+ of `README.md`, `apps/vscode/README.md`, `site/index.html` (+ ja/zh
translations):

- `README.md:179-181` / `site/index.html:750,809,906`: *"Measured on a real
  edit-and-verify loop (Claude Code, haiku, n=3, provider-reported usage): correct
  patches 3/3, input-side tokens −22%, provider cost −13%, delivered tool output
  −70%."* — **n=3 is a very small sample for a headline claim**, and this exact string
  is duplicated across at least 4 files with no shared source.
- `README.md:46` / `apps/cli/README.md:28` / `site/index.html:592`: `94%` estimated
  accessible-content reduction.
- `site/index.html:564`: `79.6%` "削減率" (reduction rate) — not found elsewhere; unclear
  if this is the same measurement as the 94% figure under a different framing, or a
  different one.
- `site/index.html:711-712`: `52.7%` / `85.9%` "estimated dynamic tool-output
  reduction" examples.

None of these were changed. Verifying or re-deriving them requires re-running the
underlying benchmark, which this session has no way to do safely (no access to the
original benchmark setup, and fabricating a "verified" number would be worse than
leaving the question open). **Flagged for the maintainer**: decide whether these
numbers are still accurate, and if so, consider a single source of truth (e.g. one
constants file or generated snippet) so the 4-way duplication cannot drift silently
the next time any of them changes.
