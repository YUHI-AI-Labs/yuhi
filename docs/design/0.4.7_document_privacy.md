# 0.4.7 — Document / PDF privacy pipeline

Status: **implemented** (issue #21 fixed; identity linkage policy Option 1 shipped).
This document originally recorded the decisions made before implementation; the
"Known limitations and permitted claims" section below records what shipped and what
did not, so neither is re-litigated or quietly reinterpreted later.

## The one rule

```text
PDF  →  text extraction  →  SAME taxonomy  →  SAME registry  →  SAME verification
```

Do **not** write PDF-specific privacy rules. Splitting the paths produces `PERSON-001` in
a CSV and `NAME-001` in a PDF for one person, which is the exact class of inconsistency
0.4.6 spent its effort eliminating.

## Identity linkage policy

This is the decision that 0.4.7 turns on, and it is a **policy choice, not a defect**.

0.4.6 does not merge two records on a personal name alone. Observed and expected:

```text
contact.csv   氏名 only          →  PERSON-001
roster.csv    氏名 + 学籍番号     →  PERSON-002        (same name, different token)
```

Merging on name alone would be worse than a weak pseudonym. Two real people named
山田太郎 would collapse onto one entity — that is not anonymisation, it is **data
corruption**, and unlike an inconsistent token it is silent and unrecoverable from the
delivered artifact.

So linkage resolves in this order, and only in this order:

```text
1. A STRONG business key
     student id, employee number, customer id, UUID, …
     (and only when it discriminates — see "discrimination guard" below)
        ↓  found → reuse that entity
2. The same-run registry
        ↓  found → reuse that entity
3. Value match on a personal name ALONE
        ↓  NOT a link → new entity
```

Applied to documents:

```text
PDF containing   学生証番号 L001 / 氏名 山田太郎
  → L001 resolves to the existing entity  → PERSON-001        ✔ consistent

PDF containing   氏名 山田太郎  (no key anywhere)
  → no linkage evidence                   → PERSON-002        ✔ correct
```

The second case is not a bug to be fixed in 0.4.7. It is the safe answer, and any change
that makes those two rows share a token must be treated as a deliberate loosening of the
policy with its own justification.

### Consequence for `text-deidentify.ts`

`deidentifyText` currently replaces known values from `directPersonalValueTokens(context)`,
which is **value-keyed**. That means a name appearing in prose reuses the token that a
table minted for the same string — table → PDF links on the name alone, while table →
table does not. That asymmetry contradicts the policy above and must be resolved during
0.4.7, in one of two ways:

- **Restrict** prose reuse to entities reachable by a strong key present in the same
  document (consistent with the policy, fewer links); or
- **Accept** value-keyed reuse for prose only, and state explicitly why a document is
  different from a second table — noting that the same-name collision risk is identical
  in both.

The first is consistent with 0.4.6. Do not leave the choice implicit in the code.

## Discrimination guard (carried from 0.4.6)

A strong key is only used for linkage when it actually discriminates. A term code, campus
code or cohort year is an operational identifier that is constant down its column; using
it for identity merges every row of a class onto one entity. The rule implemented in
`student-records.ts` compares a column's distinct values against the distinct identifier
*tuples* — not against the row count, so a degenerate export of byte-identical rows still
folds into one person.

## Requirements

- Name / contact / address detection in prose, via `text-deidentify.ts`.
- Context preservation: the document stays useful after sanitisation.
- The **original binary stays local**. The companion is generated from the SANITISED text,
  never from the raw extraction.
- Verification covers extracted text, companion markdown, generated summaries, handoff
  documents and compact representations.
- Manifest gains `documentInspection` fields.
- Tests A–D per the maintainer's spec.

## The honest limit, and what it forbids

A personal name present **only** in prose, with no tabular counterpart and no key, is not
reliably detectable. `deidentifyText` reports this as `residualRisk` with
`residualReason: "undetectable-personal-name-in-prose"`.

Therefore: publish a companion **only** when verification finds no residual direct
personal identifier. Otherwise keep the document local and report it as
context-unavailable. Relabelling an unverified companion does not make it safe.

## Fixes issue #21 (P0)

`buildSafetyPrimitives()` in `packages/core/src/background/wiring.ts` sets the
pseudonymizer to `extractTabularIdentifiers(text)`, which calls `parseDelimitedTable`
inside a `try`. Extracted PDF prose is not a delimited table, so it throws, the `catch`
returns `[]`, the pseudonymizer receives an empty forbidden list, replaces nothing — and
`BackgroundPublisher.publish()` ships the raw extraction labelled as a "Verified
companion".

## Why 0.4.7 precedes 0.5.0

Strengthening Dynamic Context while documents cannot be handled safely raises throughput
on the wrong path: it makes Yuhi leak faster. Order is: contract (0.4.6) → documents
(0.4.7) → mode UX (0.4.8) → measurement (0.4.9) → dynamic generation (0.5.0).

## Known limitations and permitted claims

Recorded once here, not restated ad hoc per surface, so a future change cannot silently
widen the claim without also updating this section.

**Detection coverage (`packages/shared/src/text-deidentify.ts`):**

- The name detector (`CJK_NAMEISH`) recognizes only 2–4 character CJK sequences. A
  single-character surname, a name of 5+ characters, and any non-CJK (e.g. Latin-script)
  personal name are not detected at all — not "detected and left unmasked", genuinely
  invisible to this pass. There is no per-document signal for this; it is a property of
  the algorithm, stated once here rather than computed per case.
- The private alias registry (`alias-registry-store.ts`) holds identifier values in a
  form that supports literal substring matching against document text — the same
  requirement `entitiesReachableInText`/`deidentifyText` already have. This is
  necessarily a matchable (not one-way-hashed) form; confidentiality comes from where it
  lives, not from obscuring its content: `.internal/`-only, `0600`/`0700`, atomic write,
  `runId`-checked on read, never written to any agent-visible surface (manifest,
  `background-status.json`, `document-index.md`, `AGENT_HANDOFF.md`, public evidence,
  or logs).
- When the registry is absent or unreadable (missing, corrupt, wrong `runId`), the
  pipeline falls back to an empty registry rather than blocking. This degrades ONLY the
  cross-format convenience (a table's `PERSON-001` will not be reused in a document from
  that same run); it does not degrade safety — every document still goes through full
  masking and independent verification before publish, exactly as it would with a
  populated registry. This is a deliberate, reviewed choice (see the module doc comment
  in `alias-registry-store.ts`), not an oversight.
- `docs/design/0.4.7_document_privacy.md`'s own linkage policy remains in force: a name
  match with no strong key present in the SAME document never reuses another entity's
  token, even if the string is identical (two different people can share a name).

**Testing gap (tracked, not hidden):** `document-index.md`'s generation code path
(`wiring.ts`'s `refreshStatus`) has no dedicated unit test with a synthetic
`manifest.json` fixture — the existing `wiring.test.ts` suite never creates one, so this
path was untested before 0.4.7 and remains so after it. It was exercised and confirmed
working during this release's own end-to-end verification (synthetic canary data,
counts only — see `docs/HANDOFF.md`), but that is a one-off run, not a regression-tested
path.

**Prohibited claims — do not use, in any surface (UI, docs, marketing, commit
messages):**

- "PDF内のすべての個人情報を除去する" / "removes all personal information from a PDF."
- "あらゆる氏名を検出できる" / "detects any personal name."
- "Document Privacy は完全匿名化を保証する" / "Document Privacy guarantees full
  anonymization."

**Permitted claims:**

- "Supported direct personal identifiers are transformed before AI delivery."
- "Documents that cannot be safely verified remain local-only."
- "Operational identifiers required for analysis are preserved."
